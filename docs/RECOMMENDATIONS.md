## [2026-09-02] Выбор стека: Astro против React

**Ситуация.** Тимофей предложил 4 варианта. Проект — лендинг строительной
компании: контента много, интерактива мало, трафик в основном мобильный и
из поиска/рекламы.

**Рекомендация.** Astro + Node/Express. SEO и скорость загрузки для
лендинга критичнее удобства разработки SPA. Astro отдаёт статический HTML
и по умолчанию не грузит JS вообще; React-SPA без SSR проигрывает в
индексации и в первом рендере на слабом мобильном.

**Запасной путь.** Если Тимофею некомфортно в Astro (он его не знает, а
сроки горят) — берём React + Vite и обязательно добавляем пререндер
(`vite-plugin-ssr` или сборку статики). Потеря в скорости приемлема, потеря
в SEO — нет. Второй запасной вариант: Astro с React-островами, тогда
Тимофей пишет привычные React-компоненты внутри Astro-страниц. Это
компромисс, который стоит предложить, если основной вариант буксует.

**Статус:** открыто — ждём ответа Тимофея в `docs/HANDOFF.md`.

## [2026-09-02] Дисбаланс зон: бэка на лендинге почти нет

**Ситуация.** По `CLAUDE.md` зоны поделены 50/50 (frontend/backend), но у
лендинга бэк — это один эндпоинт приёма заявки. Работа распределена
неравномерно, Даня окажется без задач, пока Тимофей верстает.

**Рекомендация.** Даня забирает бэк + всю инфраструктуру: домен, хостинг,
деплой, CI/CD, аналитику, интеграции (Telegram/почта/CRM). Это сопоставимый
объём и не размывает границы зон из `CLAUDE.md`.

**Запасной путь.** Если инфраструктуры окажется мало — Даня берёт часть
фронта отдельными страницами (например, каталог услуг целиком), но именно
страницами, а не файлами вперемешку: иначе два человека начнут править
одни и те же компоненты и словят конфликты в git.

**Статус:** открыто — предложено Дане, Тимофею ещё не отправлено.

## [2026-09-02] Заявки нельзя терять — нужен дублирующий канал

**Ситуация.** Заявка с формы — единственный продукт этого сайта. Если
Telegram-бот отвалился, токен протух или почта ушла в спам, клиент уже
ушёл к конкуренту, и никто об этом не узнает.

**Рекомендация.** Заявка сначала пишется в хранилище (файл или SQLite) и
только потом отправляется в уведомление. Сохранение и отправка —
независимые шаги: упавшее уведомление не должно ронять ответ клиенту.
Клиент видит «спасибо», как только заявка сохранена.

**Запасной путь.** Два канала уведомлений сразу (Telegram + почта) —
вероятность, что оба молчат, сильно ниже. Плюс раз в неделю сверять
количество записей в хранилище с числом дошедших уведомлений; расхождение
означает, что канал сломан.

**Статус:** открыто — учтено в `docs/MVP.md`, реализация за Даней.

## [2026-09-02] Форму зальют боты в первую же неделю

**Ситуация.** Открытая форма без защиты на публичном домене собирает спам
почти сразу. На фоне спама теряются живые заявки.

**Рекомендация.** Минимум без капчи (капча снижает конверсию): honeypot —
скрытое поле, которое заполняют только боты; rate limiting по IP;
проверка формата телефона на бэке. Этого достаточно против массового
спама.

**Запасной путь.** Если спам всё же пойдёт — подключаем reCAPTCHA v3
(невидимая, конверсию почти не трогает). Капчу с картинками ставим только
в крайнем случае: она отпугивает реальных клиентов сильнее, чем спасает
от ботов.

**Статус:** открыто.

## [2026-09-02] Защита main на GitHub недоступна на бесплатном плане

**РЕШЕНО 2026-09-02:** репозиторий сделан публичным, branch protection
включена — PR обязателен, 4 проверки CI, force-push запрещён, правила
действуют и на владельца. Хук `.githooks/pre-push` оставлен: он ловит
ошибку раньше, до отправки на сервер, и сообщение у него понятнее.
Запись ниже — история вопроса.

**Ситуация.** Договорились, что в `main` изменения попадают только через
PR. Попробовали закрепить это на стороне GitHub — и classic branch
protection, и rulesets отвечают 403: «Upgrade to GitHub Pro or make this
repository public». Для приватных репозиториев на бесплатном плане защита
веток недоступна. То есть правило про PR держалось только на
договорённости: `git push origin main` прошёл бы без препятствий.

**Рекомендация.** Поставили локальный хук `.githooks/pre-push` — он
блокирует push в `main` и подсказывает правильный путь. Включается на
каждой машине разово: `git config core.hooksPath .githooks`. Хук ловит
случайный push (а это 99% реальных проблем), но обходится флагом
`--no-verify` и не работает, если настройку не выполнили.

**Запасной путь.** Два варианта закрыть вопрос по-настоящему:
1. **Сделать репозиторий публичным** — защита веток станет бесплатной.
   Для лендинга это обычно приемлемо: секретов в коде нет (они в `.env`),
   а сам код не представляет коммерческой тайны. Но: репозиторий увидят
   все, включая заказчика и конкурентов, вместе с историей коммитов и
   рабочей перепиской в `docs/HANDOFF.md`. Решение владельца, не Claude.
2. **GitHub Pro** (~$4/мес) — приватность сохраняется, защита включается.

Пока ни один вариант не выбран, единственная защита — хук и дисциплина.

**Статус:** открыто — вопрос вынесен пользователю, задача в `TODO.md`.

## [2026-09-02] Рынок — Украина: что это меняет

**Ситуация.** Сайт рассчитан на Украину. Часть решений в документах была
записана по инерции под российский рынок и оказалась неверной.

**Что исправлено:**
- **Аналитика:** Яндекс.Метрика → Google Analytics 4. Российские сервисы
  в Украине заблокированы, Метрика просто не будет работать у части
  посетителей.
- **Хранение данных:** требования локализации нет. Российский 152-ФЗ к
  проекту не относится; украинский закон «Про захист персональних даних»
  не требует держать базу внутри страны. Европейский хостинг подходит.
- **Язык:** украинская версия должна загружаться по умолчанию для
  компаний, зарегистрированных в Украине (ст. 27 Закону «Про забезпечення
  функціонування української мови як державної»). Это влияет на вёрстку с
  самого начала, а не «переведём потом». Стоит подтвердить у юриста
  заказчика.
- **Домен:** ориентир `.ua` / `.com.ua`, не `.ru`.
- **Телефоны:** формат `+380`, валидацию на бэке писать под него.

**Рекомендация.** Российский хостинг не рассматривать вообще — санкции,
блокировки и репутация у заказчика. Ориентир — Европа (близкая
латентность) или украинские провайдеры.

**Запасной путь.** Если европейский хостинг окажется неудобен по оплате —
украинские провайдеры (Mirohost, HostPro, DeltaHost) закрывают ту же
задачу, обычно дороже за те же ресурсы, но с местной поддержкой и оплатой.

**Статус:** принято — документы поправлены.

## [2026-09-02] Автодеплой лучше настроить до первого релиза

**Ситуация.** Деплой руками — это забытые шаги, «а я не залил» и правки
прямо на проде. На двоих без общего процесса это станет проблемой быстро.

**Рекомендация.** Автодеплой из `main`: смерджили PR → сайт обновился сам.
Это ровно то, зачем заводили ветки dev/main. Заводить лучше на пустом
проекте — на готовом настраивать больнее.

**Запасной путь.** Если автодеплой не заведётся с выбранным хостингом —
скрипт деплоя в репозитории (`deploy.sh`), одинаковый у обоих. Хуже, чем
CI, но лучше, чем «залил как помню».

**Статус:** отклонено в пользу GitHub Pages — проект оказался учебным,
см. запись «Проект учебный — упростили инфраструктуру» выше. Разбор
оставлен: пригодится, если проект станет настоящим.

## [2026-09-02] Проект учебный — упростили инфраструктуру

**Ситуация.** Выяснилось, что проект тренировочный: цель — научиться
работать вдвоём через Claude Code, а не запустить сайт для реального
заказчика. Настроенная связка Cloudflare Pages + Hetzner VPS для этого
избыточна: аккаунты, сервер, systemd, SSH-ключи — время уходит на
администрирование, а не на обучение.

**Рекомендация.** Всё на GitHub, ничего не покупаем:
- репозиторий сделан **публичным** — это разом открыло GitHub Pages и
  branch protection, оба бесплатно (на приватных репозиториях бесплатного
  плана недоступны ни то, ни другое);
- фронт публикуется на GitHub Pages из `main`;
- бэкенд **не выкладывается** — запускается локально командой
  `npm run dev`.

Workflow'ы деплоя на Cloudflare и VPS удалены, чтобы не гнили в
репозитории. Понадобятся — восстанавливаются из истории git:
`git log --diff-filter=D --name-only` найдёт коммит с удалением.

**Запасной путь.** Понадобится реальный работающий бэк в интернете:
1. **Cloudflare Workers** — бесплатно, без сервера, но API отличается от
   Express, код придётся адаптировать.
2. **VPS** (разбор в записи ниже) — код Express переезжает без изменений,
   но требует настройки и денег.
Выбор откладываем: пока форма нужна только на локальной машине, платить
и администрировать не за что.

**Цена решения, которую надо принять осознанно:** на опубликованной
странице форма работать не будет. Для учебного проекта приемлемо, для
показа заказчику — нет.

**Статус:** принято.

## [2026-09-02] Почему фронт и бэк в разных местах

**Ситуация.** Проще было бы поставить всё на один VPS: один счёт, одно
место настройки. Выбрали разнести — стоит зафиксировать почему, чтобы
через полгода не «упростили» обратно.

**Рекомендация.** Фронт на Cloudflare Pages, бэк на VPS:
- статика с CDN грузится быстрее, а скорость на мобильном для лендинга
  прямо влияет на конверсию;
- Cloudflare даёт бесплатную защиту от DDoS — для украинского сайта это
  не теоретический риск;
- падение бэка не уносит сайт: страницы открываются, не работает только
  форма. На одном сервере падение унесло бы всё;
- откат фронта — кнопка в панели Cloudflare, секунды.

**Запасной путь.** Если возня с двумя площадками окажется тяжелее пользы
(например, бэк так и останется в один эндпоинт) — переехать на один VPS
и раздавать статику через тот же nginx. Потеряем CDN и защиту от DDoS,
получим одно место настройки. Обратный переезд дешёвый: статика есть
статика.

**Статус:** принято.
