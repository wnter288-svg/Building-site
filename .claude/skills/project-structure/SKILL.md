# Чистая структура проекта

Цель — чтобы человек или другой ИИ, впервые открывший репозиторий, за
пару минут понял, где что лежит и куда класть новое. Всё остальное
вторично.

Действующая карта — `docs/STRUCTURE.md`. Она первоисточник: сверяйся с
ней и обновляй её.

## Правила раскладки

1. **Две зоны.** Фронт — только в `frontend/`, бэк — только в `backend/`.
   Смешивать нельзя: зоны принадлежат разным людям (см. `CLAUDE.md`).
2. **Корень репозитория чистый.** В корне только: `README.md`,
   `CLAUDE.md`, `TODO.md`, `.gitignore`, конфиги уровня репозитория,
   папки `docs/`, `.github/`, `.claude/`, `frontend/`, `backend/`.
   Файл, брошенный в корень «на время», остаётся там навсегда.
3. **Документация — в `docs/`.** Исключения — три точки входа в корне
   (README, CLAUDE, TODO).
4. **Имя говорит о содержимом.** `components/`, `pages/`, `routes/`,
   `services/`, `middleware/` — хорошо. `utils/`, `helpers/`, `common/`,
   `misc/`, `stuff/`, `new/`, `tmp/` — свалки: туда складывают то, для чего
   не придумали места, и через месяц там ничего не найти. Заводить их
   нельзя. Если очень нужно — назови по смыслу: `formatting/`,
   `validation/`.
5. **Плоско, пока можно.** Вложенность больше трёх уровней внутри зоны —
   повод остановиться и подумать. Папка ради одного файла не нужна.
6. **Один файл — одна ответственность.** Больше ~300 строк и несколько
   несвязанных задач внутри — делим.
7. **Секретов в репозитории нет.** Ключи и токены — в `.env` (он в
   `.gitignore`), в репозиторий кладём `.env.example` с пустыми
   значениями.
8. **Мёртвого кода нет.** Закомментированные блоки, `old/`, `backup/`,
   `index-copy.js`, «пусть полежит» — удаляем. История есть в git, она для
   этого и нужна.

## Проверка структуры

Когда просят «проверь структуру» — пройди по списку и доложи:

1. Совпадает ли реальное дерево с `docs/STRUCTURE.md`?
2. Есть ли файлы в корне, которых там быть не должно?
3. Есть ли папки-свалки (`utils`, `helpers`, `common`, `misc`)?
4. Есть ли файлы фронта в `backend/` и наоборот?
5. Есть ли мёртвый код, копии файлов, закомментированные куски?
6. Есть ли секреты в отслеживаемых файлах? (`.env` в `.gitignore`?)
7. Есть ли файлы, которые никто не импортирует?
8. Понятно ли по именам папок, что внутри?

Формат ответа: список находок, каждая — что нашёл, чем плохо, что
предлагаю. Дальше спроси, что чинить. Не переделывай всё разом молча.

## Как безопасно переносить файлы

Перенос ломает импорты. Порядок обязателен:

1. **Убедись, что рабочее дерево чистое** — `git status`. Есть
   незакоммиченное — сначала коммить, иначе при откате потеряешь работу.
2. **Найди все ссылки на файл** до переноса: импорты, роуты, конфиги,
   пути в CI, ссылки в документации. Ищи по имени файла и по пути.
3. **Переноси через `git mv`**, а не удалением с созданием заново — так
   git сохранит историю файла.
4. **Почини все найденные ссылки.**
5. **Проверь, что не осталось битых путей** — ещё раз поиском по старому
   пути. Ноль вхождений.
6. **Прогони `/test-project`** — сборка и тесты должны проходить.
7. **Обнови `docs/STRUCTURE.md`**: дерево, дату, запись в «Историю
   структурных решений» с причиной переноса.
8. **Один коммит — один осмысленный перенос.** Не мешай перенос файлов с
   правкой их содержимого: в таком диффе невозможно понять, что
   изменилось.

## Перед тем как завести новую папку

Спроси себя: где это стал бы искать человек, который проект не писал?
Если ответ не совпадает с задуманным местом — место выбрано неправильно.

Если новая папка меняет принятую раскладку — не решай сам. Опиши
предложение пользователю, а после согласования запиши решение и причину в
«Историю структурных решений» в `docs/STRUCTURE.md` и предупреди напарника
через `docs/HANDOFF.md`.

## Ограничения

- Не трогай чужую зону без причины (`CLAUDE.md`). Нужно тронуть — сначала
  `docs/HANDOFF.md` и предупреждение пользователю.
- Не делай массовый рефакторинг структуры «заодно» с задачей. Отдельная
  задача, отдельный коммит, отдельный PR.
- Не переименовывай то, на что ссылается внешний мир (URL страниц, пути
  API), не предупредив: это ломает ссылки и SEO.
