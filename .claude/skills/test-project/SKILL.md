# Проверка проекта

Два прогона в одном: **работоспособность** (оно вообще запускается и
делает то, что должно) и **безопасность** (его нельзя легко сломать или
залить спамом).

Проект — лендинг, у которого одна бизнес-задача: довести заявку от клиента
до владельца компании. Поэтому главный тест всегда один: **заявка с формы
доходит до адресата**. Если это не работает, остальное неважно.

## Порядок

Проверки идут от дешёвых к дорогим. Упало на раннем шаге — чини и
перезапускай, дальше не иди: следующие проверки всё равно наврут.

### 0. Что вообще есть

Осмотрись перед запуском команд:
- Есть ли `frontend/`, `backend/`, `package.json` в них?
- Какие скрипты объявлены в `package.json` (`build`, `test`, `lint`,
  `dev`)?
- Проект ещё не начат? Тогда не выдумывай прогон — доложи, что проверять
  нечего, и на этом всё.

Запускай только те шаги, для которых есть код. Отсутствующий шаг — это
«пропущено», а не «пройдено». Никогда не отмечай непроверенное как
пройденное.

### 1. Работоспособность

| Шаг | Как | Что значит провал |
|---|---|---|
| Зависимости ставятся | `npm ci` (или `npm install`) в каждой зоне | сломан `package-lock.json` или конфликт версий |
| Проект собирается | `npm run build` | до прода не доедет |
| Линт чистый | `npm run lint` | стиль/ошибки, которые заметит только человек |
| Тесты проходят | `npm test` | сломана логика |
| Сервер стартует | запусти `backend`, дождись порта, останови | конфиг или переменные окружения |
| Эндпоинт отвечает | POST заявки с корректными данными → 2xx | форма не работает |
| Фронт открывается | собери и открой страницу | пустая страница, ошибки в консоли |

**Главный сквозной тест:** отправить заявку через форму фронта и убедиться,
что она (а) сохранилась в хранилище, (б) ушла в канал уведомлений. Обе
части обязательны — заявка, о которой никто не узнал, потеряна.

**Проверь и негативные случаи**, не только счастливый путь:
- пустое имя / пустой телефон → внятная ошибка, не 500;
- телефон в кривом формате → отказ с понятным сообщением;
- очень длинная строка в поле → не роняет сервер;
- две одинаковые заявки подряд → не дубль в хранилище.

### 2. Безопасность

| Проверка | Как | Почему важно |
|---|---|---|
| Секретов нет в репозитории | поиск по `API_KEY`, `TOKEN`, `PASSWORD`, `SECRET`, `BOT_TOKEN`, длинным base64/hex-строкам; `git log -p` на всякий случай | утёкший токен бота = чужие люди читают ваши заявки |
| `.env` не отслеживается | `.env` есть в `.gitignore`, `git ls-files` его не показывает | то же самое |
| `.env.example` есть и пустой | глазами | напарник не поймёт, какие переменные нужны |
| Зависимости без дыр | `npm audit` в каждой зоне | чужой код в вашем проде |
| Валидация на бэке | входные данные проверяются на сервере, а не только в браузере | проверку в браузере обходят за минуту |
| Rate limiting | много запросов подряд с одного IP → 429 | форму зальют спамом |
| Honeypot | скрытое поле в форме, заполнено → заявка тихо отбрасывается | отсекает ботов без капчи |
| CORS настроен | запрос с чужого домена не проходит | чужие сайты не шлют заявки от вашего имени |
| Заголовки безопасности | `helmet` или аналог: CSP, X-Frame-Options, nosniff | базовая гигиена |
| Ошибки не текут наружу | 500 не отдаёт стектрейс и пути на диске | подсказка атакующему |
| XSS в выводе | если данные заявки где-то показываются — экранируются ли | внедрение скрипта |
| Инъекции | параметры в запросах к хранилищу параметризованы, не склейка строк | подмена запроса |
| HTTPS | на проде есть, HTTP редиректит на HTTPS | телефоны клиентов открытым текстом |
| Персональные данные | телефоны в логи не пишем; на форме — согласие на обработку ПД | это ещё и требование закона |

### 3. Отчёт

Кратко, в чат. Формат:

```
РАБОТОСПОСОБНОСТЬ
  ✅ Сборка frontend
  ✅ Сборка backend
  ❌ Тесты backend — 2 упали (см. ниже)
  ⏭️ Линт — не настроен

БЕЗОПАСНОСТЬ
  ✅ Секретов в репозитории нет
  ⚠️ Rate limiting не настроен
  ❌ .env отслеживается git

КРИТИЧНО (чинить до PR в main):
  1. .env в репозитории — токен видно всем, отозвать и перевыпустить
  2. ...

СТОИТ ПОЧИНИТЬ:
  1. ...
```

Обозначения: `✅` пройдено, `❌` провал, `⚠️` замечание, `⏭️` пропущено
(нечего проверять).

## После прогона

- Нашёл проблемы — заведи их в `TODO.md`, иначе забудутся.
- Критичные находки по безопасности — сразу в чат отдельно, не прячь в
  общий список.
- Нашёл утёкший секрет — **скажи пользователю немедленно**: токен нужно
  отозвать и перевыпустить. Удаления файла недостаточно, он остался в
  истории git.
- Прогон перед PR в `main` — обязателен (см. `CLAUDE.md`). Красный прогон
  в `main` не заливаем.

## Ограничения

- Не чини найденное молча в том же заходе — сначала отчёт, потом решение
  пользователя. Исключение — утёкший секрет: о нём говори немедленно.
- Не пиши тесты «чтобы были зелёные». Тест, который ничего не проверяет,
  вреднее отсутствующего: он создаёт ложную уверенность.
- Не гоняй нагрузочные и проникающие тесты по чужим хостам. Проверяем
  только свой проект локально.
- Не выдумывай результат непройденной проверки. Не смог запустить — так и
  напиши.
