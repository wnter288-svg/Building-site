# Рекомендации и запасные пути

Задача навыка — чтобы обдуманное один раз не приходилось обдумывать
заново. Разобрал развилку — запиши. Основной путь встал — достань
запасной, он уже лежит готовый.

Файл: `docs/RECOMMENDATIONS.md`.

## Что писать в чат, а что в файл

**В чат — только предложения и улучшения.** Коротко: суть, почему,
что предлагаю. Без пересказа файла и без стен текста.

**В файл — разбор целиком:** ситуация, рекомендация с обоснованием,
запасной путь, статус. Файл — память между сессиями; чат её не хранит.

Не зачитывай пользователю файл вслух. Скажи «записал в
`docs/RECOMMENDATIONS.md`» и дай выжимку в 2-3 строки.

## Когда делать запись

- Выбрали одно из нескольких решений — записывай, **почему отклонили
  остальные**. Через месяц вопрос вернётся, и без причины его начнут
  решать заново.
- Приняли решение, в котором не уверены.
- Увидел риск: что-то может потеряться, сломаться, стоить денег.
- Пользователь спросил совета по развилке.
- Основной путь не сработал — обнови статус и запиши, чем он не подошёл.

Мелочи не записывай. Файл, забитый очевидностями, перестают читать.

## Формат записи

```markdown
## [ГГГГ-ММ-ДД] Заголовок одной строкой

**Ситуация.** Что происходит и почему это вообще вопрос.

**Рекомендация.** Что предлагаю и — обязательно — почему именно это.

**Запасной путь.** Что делаем, если основной не сработает. Конкретно,
не «придумаем что-нибудь».

**Статус:** открыто / принято / отклонено — с причиной.
```

Статус поддерживай в актуальном виде. Приняли решение — поменяй
`открыто` на `принято`. Запись с устаревшим статусом вводит в
заблуждение.

## Как думать про запасной путь

Запасной путь — не «а если совсем всё плохо», а **конкретный второй
вариант с ценой**. Хороший запасной путь отвечает на три вопроса:

1. По какому признаку поймём, что основной путь не сработал?
2. Что делаем вместо него?
3. Чем за это платим (скорость, деньги, качество, время на переделку)?

Пример плохого: «если Astro не пойдёт — возьмём что-нибудь другое».
Пример хорошего: «если Тимофей за неделю не разберётся в Astro — берём
React + Vite с пререндером; теряем в скорости загрузки, SEO сохраняем;
переделка вёрстки не нужна, меняется только сборка».

## Достать рекомендацию обратно

Когда упёрлись в проблему — **сначала загляни в
`docs/RECOMMENDATIONS.md`**: возможно, план Б для неё уже написан.
Нашёл — напомни пользователю, а не придумывай заново.

## Продвигать удобства

Отдельная обязанность: **предлагать инструменты, которые экономят время и
спасают от потерь**, и настаивать, если ими не пользуются. Пользователь
просил не просто советовать, а подталкивать.

Что продвигать и когда:

| Инструмент | Когда напомнить | Аргумент |
|---|---|---|
| Коммиты почаще | накопилось много несохранённых изменений | несохранённая работа теряется целиком, а не частями |
| Ветка `dev`, PR в `main` | пушат мимо процесса | в `main` живёт рабочий сайт, его ломать нельзя |
| CI (`.github/workflows/ci.yml`) | добавили сборку или тесты | проверка на каждый push, а не «у меня локально работало» |
| Автодеплой из `main` | появился хостинг | смерджил PR — сайт обновился; руками забывают шаги |
| Branch protection на `main` | как только появился прод | защита от случайного пуша в прод |
| `.env` + `.env.example` | появился первый ключ или токен | секреты в git утекают навсегда |
| Issues на GitHub | задачи из `TODO.md` расползлись | обсуждение рядом с задачей |
| Бэкап заявок | появился приём заявок | заявка — продукт сайта, терять нельзя |

Как настаивать правильно: назови конкретную цену бездействия («без
branch protection любой пуш в main выкатывается на живой сайт»), предложи
сделать это сейчас и сам. Не повторяй одно и то же требование каждую
сессию — если пользователь осознанно отказался, запиши отказ в
`RECOMMENDATIONS.md` со статусом `отклонено` и причиной, и не возвращайся
к вопросу, пока обстоятельства не изменились.

## Ограничения

- Одна рекомендация за раз, а не список из десяти. Десять рекомендаций
  не выполняет никто.
- Рекомендация без «почему» — это указание, ему не будут следовать.
- Не рекомендуй сложное там, где хватит простого. Лендингу не нужны
  Kubernetes, микросервисы и очереди сообщений.
- Не выдавай догадки за факты. Не уверен — так и скажи.
